# Groth16 batch-verification prototype (Phases 0–1 of Perf.md §9.4)

**Status: experimental, disposition postponed.** This is a standalone proof-of-concept, not integrated with `zerod` in any way. It does not touch `main.cpp`, the FFI layer, or any consensus code. See `Perf.md` §0.1a for the live decision this prototype feeds into (hand-port this approach vs. adopt `zcash/sapling-crypto`'s `BatchValidator` directly) — that decision is unresolved, and this code's fate (kept as a reference, extended into Phase 2, or discarded in favor of the adopt-upstream path) depends on it. Do not build on top of this without reading that section first.

## What this proves

A hand-ported random-linear-combination Groth16 batch verifier, built entirely from primitives already present in Zero's **pinned** `bellman`/`pairing` crates (no crate-version upgrade), tested against real Groth16 proofs generated by `bellman`'s own MiMC/BLS12-381 test circuit (not synthetic/mocked proofs).

Result, run 6 times with fresh randomness each time (see `Perf.md` §9.4 for the full write-up):
- N = 1, 2, 8, 64, all-valid proof batches: batch accept exactly matches per-proof `verify_proof`, every run.
- N = 2, 8, 64, one corrupted proof among N: batch correctly rejects, every run.
- The pinned 2018-era `bellman 0.1.0`/`pairing 0.14.2` crate pair builds clean under a modern Rust toolchain (warnings only, no errors) — confirmed no toolchain-pinning workaround is needed to build or extend this.

This validates the core math (§9.4 Phase 1's exit criterion) — it does **not** validate an FFI design, a `main.cpp` integration, or consensus-safety; those are Phase 2 onward, not started, blocked on the §0.1a decision.

## Setup (this code is not self-contained — read this before running)

This crate has path dependencies on Zero's pinned `librustzcash` monorepo (commit `06da3b9ac8f278e5d4ae13088cf0a4c03d2c13f5`, matching `depends/packages/librustzcash.mk`), fetched as a sibling checkout **directly inside `ZeroPerf/`** (`ZeroPerf/librustzcash-pinned/`, next to `ZeroPerf/groth16-batch-poc/` — `Cargo.toml`'s path deps are `../librustzcash-pinned/bellman` and `../librustzcash-pinned/pairing`, one level up from this directory). That checkout is **not vendored into this repo** — it's Zero's existing pinned dependency, fetched fresh, not new third-party source belonging to `ZeroPerf`. `.gitignore`d if fetched inside the repo tree; see below.

```bash
# From the ZeroPerf repo root:
git clone --no-checkout https://github.com/zcash/librustzcash.git librustzcash-pinned
cd librustzcash-pinned
git fetch --depth 1 origin 06da3b9ac8f278e5d4ae13088cf0a4c03d2c13f5
git checkout -q FETCH_HEAD
cd ..

cd groth16-batch-poc
cargo run --release
```

Verified this session: full unshallowed `git clone` of `zcash/librustzcash` times out (large history) — `git init && git remote add && git fetch --depth 1 origin <sha> && git checkout FETCH_HEAD` is the fast path that actually works, if `clone --no-checkout` above ever has the same issue.
```

Full shallow-clone timed out when tried without `--depth 1` (the full history is large); the `git init` + `fetch --depth 1 origin <sha>` + `checkout FETCH_HEAD` sequence above is the fast path that actually worked.

## Files

- `src/main.rs` — the prototype itself: the MiMC demo circuit (copied from `bellman/tests/mimc.rs` in the pinned checkout, used only as a real-proof generator), the hand-ported `batch_verify` function (the actual subject of this prototype — see its doc comment for the algorithm and which pinned-crate primitives it relies on), and a `main()` that runs the N=1/2/8/64 all-valid and corrupted-proof test matrix and prints PASS/FAIL.
- `Cargo.toml` / `Cargo.lock` — pins the exact transitive dependency graph this was built and tested against (`rand 0.4.6`, `byteorder 1.5.0`, etc.), so a future rebuild reproduces the same versions rather than whatever `rand 0.4`'s latest patch happens to resolve to at build time.
